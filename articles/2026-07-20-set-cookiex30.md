# クラッシュゼロの監視が見逃した、Set-CookieひとつでX投稿が止まった30分

7月17日、私が毎日ブラウザで自動運用しているXアカウントへの投稿が、突然失敗し始めました。x.com/homeを開くと、ログイン画面へのリダイレクトすら起きず、そのURLのまま「Something went wrong」とだけ表示されます。実際に投稿処理が返してきたエラーはこれでした。

```
x_session_logged_out_stale_auth_token
```

真っ先に疑ったのは「ブラウザが落ちた」でした。だが監視ログを見ると、直近のブラウザ再起動は13時41分。それ以降、クラッシュも再起動もゼロ。プロセスは生きたまま、なのに投稿だけが死んでいました。結論を先に書くと、原因は監視対象のサイト一覧にx.comが入っていなかった、ただそれだけでした。同じ日にはもう1件、production環境の実行ログを自分の手作業コマンドで消してしまう事故も起きています。同じようにブラウザ自動化でSNS投稿を回している人には、そのまま自分のパイプラインでも起こりうる話です。

## ログインを支える複数のCookie

多くの人は「ログインしている」を、ID・パスワードで発行された1本の鍵を持っている状態だとイメージします。実際にブラウザの中で起きているのは違います。X（旧Twitter）のようなサービスは、複数のCookieの組み合わせでログイン状態を成立させています。

代表的なのが2つ。ひとつは`auth_token`、これがいわゆる「本体のログイン証明」にあたります。もうひとつが`ct0`と呼ばれるCSRFトークンです。CSRFとは、悪意あるサイトが被害者のログイン状態を勝手に利用して不正な操作を行う攻撃(クロスサイトリクエストフォージェリ)のこと。`ct0`はその対策として発行される、リクエストごとの「このリクエストは本当にあなたが今送ったものです」という証明書のようなCookieです。

厄介なのは、この`ct0`がサーバー側の都合で定期的に再発行(ローテーション)されること。サーバーは新しい`ct0`を`Set-Cookie`ヘッダーでブラウザに渡しますが、そのブラウザが該当サイトに対して何のリクエストも送っていなければ、新しい値を受け取る機会そのものがありません。結果、`auth_token`は有効なまま、`ct0`だけが静かに古くなり、Xの画面側がクラッシュしたような表示(Something went wrong)を返します。

## 30分ごとのCookieスナップショット

私が使っているシステムには、ログイン状態のCookie群を定期的にバックアップする仕組みがあります。その履歴を時系列で突き合わせたところ、次の状態が見えてきました。

| 時刻 | 出来事 | auth_token | ct0 |
|---|---|---|---|
| 13:41 | 直近のブラウザ再起動 | - | - |
| 16:01 | 最後の完全ログイン状態 | あり | あり |
| 16:31 | 次のスナップショット | あり | 消失 |

16時01分の時点では`auth_token`と`ct0`が両方そろっていました。これが最後に完全にログインできていた瞬間です。次のスナップショットである16時31分には、`ct0`だけが消えていました。

つまり、この30分の間のどこかで`ct0`のローテーションが起き、それを受け取るはずのリクエストが一度も発生しませんでした。

タイトルの「30分」は、`ct0`が健全から消失に切り替わった、この16時01分から16時31分までのスナップショット間隔を指しています。一方、実際に投稿が止まっていた時間、つまり気づいて後述する3つの恒久対策のうち最初の2つをコミットする(17時38分と17時45分)までの時間は、長く見積もっても1時間40分程度でした。監視対象リストにx.comが漏れていたこと自体は、システムを動かし始めた当初から数か月気づかれずに残っていた欠陥ですが、それが実際の投稿停止として表に出て塞がれるまでの時間はこの範囲に収まっています。

原因はもっと単純でした。私のシステムには、ログインが必要な複数のサイトを定期的に開いて「まだ生きてますか」と確認する監視ジョブがあります。30分おきに動くこのジョブが巡回していたのは2サイトだけで、そこにx.comは含まれていませんでした。つまりXに対しては、`ct0`を再発行させるきっかけとなるアクセスが構造的に一度も起きない設計になっていました。監視の「対象リストに入れ忘れる」というだけのミスが、半年近く稼働してきたシステムの投稿機能を静かに止めていたことになります。

## 非公式Xクライアント開発者が抱える同じ壁

このCookie構成の問題は、Xの非公式クライアントを作っている開発者コミュニティでも共通の壁として扱われています。★4,561の[d60/twikit](https://github.com/d60/twikit)は、ログイン状態をCookie jar全体としてまるごと保存し、保存済みファイルがあれば`login()`処理そのものを完全にスキップする設計を取っています。理由は明快で、ログイン処理を繰り返すこと自体がX側から見て不審な挙動として扱われるからです。

★2,586の[vladkens/twscrape](https://github.com/vladkens/twscrape)も同様に、Cookie一式とHTTPヘッダーをアカウント単位でまとめて保存・復元し、コード内で`assert "ct0" in client.cookies`と明示的に`ct0`の存在をチェックしています。[the-convocation/twitter-scraper](https://github.com/the-convocation/twitter-scraper)にいたっては、ログイン判定の関数が`ct0`と`auth_token`の両方を要求する設計で、`ct0`だけでは不十分であり`auth_token`がなければ401エラーが返ってくると明言しています。

つまり結論は同じところに集約します。Xのログインを機械的に維持しようとする実装は、みな「`ct0`と`auth_token`のペア」を最低ラインとし、レスポンスのたびに`Set-Cookie`をCookie jarへ反映してローテーションに追従する設計を取っています。今回のケースはこの最低ラインを満たすための仕組み(定期アクセス)が、対象リストの記載漏れによって存在しなかった、というだけの話でした。

## 恒久対策として3つ変えた

原因が分かったあと、私は3つの手を打ちました。

Step 1、監視対象のサイト一覧にx.comのホーム画面と、別サービスであるZennのダッシュボード画面を追加したこと。変更前後の一覧はこうなります。

```
変更前: 2サイト
変更後: 4サイト (x.com/home, Zennダッシュボードを追加)
```

これで30分ごとに強制的にアクセスが発生し、`ct0`のローテーションを毎回きちんと受け取れるようになります。この監視が止まった場合は即座に通知が飛ぶようにもしました。

Step 2、Cookie群のバックアップを取る瞬間に、`auth_token`と`ct0`が両方そろっているかを確認するチェックを追加したこと。片方だけの半死状態のCookieを新しい正としてバックアップしてしまうと、直前まで健全だったバックアップまで上書きして失ってしまいます。そのため、両方そろっていない場合は、直前の健全なバックアップが存在する限り、新しい方を採用せず古い方を維持するようにしました。

Step 3、それでもログアウト状態が検知された場合に限り、パスワードによる再ログインを1回だけ自動で試みる仕組み。ただし6時間のクールダウンを設けて連打を防いでいます。ログイン処理の繰り返しがX側から不審な挙動として扱われる、というtwikitの知見をそのまま踏まえた設計です。

なお、この再ログインが携帯電話番号でのSMS認証を要求してきた場合は、そこで自動処理を止める設計にしてあります。この壁を越える手段は今のところ用意していません。

## もうひとつの原因: 手動で打った確認コマンド

同じ日に起きたもう1件の事故は、原因も対処もまったく違うのに、教訓だけは同じ形をしていました。ある処理が正常終了した証拠として残っているはずの実行ログの1行が、記録からごっそり消えていたのです。

犯人は自動テストではありませんでした。自動テストと本番は別々の実行環境に隔離されていて、その隔離自体は正しく機能していました。本当の犯人は、私自身がその日のうちに手で打った、ちょっとした確認のつもりのコマンドです。本番のログファイルのパスに対して直接削除コマンドを実行し、バックアップも取らずにファイルを消していました。その日の本物の実行結果は、たまたま直前に取っていたバックアップの断面よりも後に生成されたものだったため、復元する手段がありませんでした。結局、汚染されたログを取り除いたうえで該当の処理をもう一度正規に実行し直し、新しい正しい記録を作り直すしかありませんでした。

## 自動パイプラインと手動コマンド、危険度の差

この2つの出来事から得た教訓は同じ形をしています。「プロセスが落ちていない」「クラッシュが起きていない」という状態は、システムが健全に機能していることの証拠にはなりません。ログイン状態を構成するCookieの一部だけが静かに死んでいても、プロセス監視の目には何も映りません。

そして、production環境を実際に壊すのは、たいてい自動化されたパイプラインではなく、エンジニア自身がその場しのぎで打つ手動の確認コマンドです。特にproductionの実データに直接触れる操作(今回で言えば削除コマンド)を打つ前には、「これは自動テストと同じ隔離の下にあるか」を自問し、なければ先にバックアップを取ってから実行するべきでした。

監視の設計を見直すときは、「稼働しているように見える指標」と「実際に機能している指標」を分けて考える必要があります。前者はプロセスの生存、後者はその先で本当に必要な処理(この場合はログイン維持に必要なCookieの再発行)が届いているかどうかです。両方を混同すると、今回のように何ヶ月も気づかれない穴が生まれます。

この一連の自動化は、[aniccaai.com](https://aniccaai.com) のプロジェクトの一部として動いています。
