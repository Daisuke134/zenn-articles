## [0] 最初に

- この記事の結論は、評価スコアを単独で「価値」と読まないことです。スコアは候補、比較相手、評価器、提示順、検証データの組み合わせから出ます。
- 私の見出しは0.00点になりました。比較相手を開くと、和解金の報道と製品発表でした。この結果だけで、見出しの価値を判断するのは無理でした。
- FairEvalは提示順だけでLLMの順位が歪む例を報告し、IF-RewardBenchは2026年のベンチマークでも、人間より低い評価器の相関を示しています。
- おすすめする人は、LLMの採点結果を改善ループや報酬に使っている人です。おすすめしない人は、数字一つで品質を確定したい人です。

## [1] 0.00点を見た夜

見出し候補を評価器に渡した夜、私の候補は0.00点になりました。

最初は「見出しが弱かった」と受け取りかけました。けれど、採点表だけでは何に負けたのか分かりません。そこで比較に使われた相手を開きました。そこには、和解金をめぐる速報と、新製品の発表が並んでいました。

速報とエッセイの見出しを同じ順位表に入れたら、速報のほうが強く見えるのは自然です。読者がその日のニュースを探しているなら、速報は勝ちます。技術記事の反転や個人の実感を測る比較としては、別の問いです。

0.00は、私の見出しの価値を直接測った数字ではありません。その比較で返された結果です。

この記事を読むと、評価器を捨てるか信じるかの二択ではなく、スコアの隣に何を保存すればよいかが分かります。

## [2] 評価スコア

評価器は、回答や文章を別のモデルに採点させる仕組みです。LLM-as-a-Judgeと呼ばれることもあります。生成した候補を評価器へ渡し、点数、順位、採用か不採用かを返させます。

私はこの仕組みを使います。ただし、最終判定ではなく、次に調べる候補を絞る一回目の採点としてです。SkillOptのような仕組みは、評価された軌跡からskill文書を編集し、held-out validation、つまり編集に使っていない検証データで改善を確かめます。

ただし、評価器の点数は温度計の数字とは違います。温度計は、設計された尺度と対象の温度を対応させます。評価器の点数は、少なくとも次のものに依存します。

| 点数を動かすもの | 確認する問い |
|---|---|
| 候補 | 何を比べているか。長さ、正しさ、売れそうかを混ぜていないか |
| 比較相手 | 同じ種類の候補か。速報とエッセイを混ぜていないか |
| 評価器 | どのモデル、どの指示、どの採点形式か |
| 提示順 | AとBを入れ替えても同じ判断か |
| 検証データ | 編集に使っていない例でも改善したか |

この五つが残っていない点数は、再現できないレシートです。

## [3] 評価器の壊れ方

### 順序バイアス

WangらのFairEvalは、LLMを回答の審判にしたとき、候補の提示順を変えるだけで順位が大きく変わることを調べました。GPT-4を評価器にした例では、Vicuna-13BがChatGPTに80問中66問で勝ったと報告しています。ここで重要なのは、Vicunaが本当に優れていたという意味ではなく、順番を変えるだけで勝敗の見え方を操作できたことです。

当時の記録には、モデル名や版、候補全文、順序別の得点表が残っていません。後ろの選択肢を拾ったという観測は、再現可能な実験としては扱わないことにします。採点理由の文章がもっともらしくても、判断の独立性は証明できません。

FairEvalが提案した対策は、複数の根拠を書かせること、順序を変えた結果をまとめること、難しい例だけ人間に回すことです。単に「公平に採点して」と書くより、比較の構造を変える対策です。

### 自己修正の限界

Huangらは、外部の正解やフィードバックを使わず、モデルの内部だけで推論を自己修正させる実験を調べました。うまく直せないだけでなく、修正後に性能が落ちる場合もありました。

これは文章の評価にも通じます。評価器が「前の案より良い」と言っても、同じ評価器だけで直し続けると、評価器の好みへ寄っただけかもしれません。外部の正解、別形式のチェック、未使用データが必要になります。

### 新しいベンチマーク

IF-RewardBenchの著者は、指示に従えているかを測る評価器向けのベンチマークを作りました。842個の指示、6,011個の回答、9,145個の選好関係を用意し、複数回答の順位付けを調べています。

結果は厳しいものでした。制約評価のKendall相関は、人間の0.755に対して、最高のGemini-3-Proでも0.609でした。複数ターン、system prompt、主観的な文体制約、制約の数が増えると評価は難しくなります。

つまり、評価器が新しくなれば問題が消える、という話ではありません。IF-RewardBenchの著者は、回答の品質や指示の複雑さが上がると評価が難しくなると報告しています。

## [4] 報酬汚染

ここでいう報酬は、モデルを改善する方向を決める数字です。点数が高い案を残すなら、その点数が報酬になります。

報酬の汚染は、モデルが悪意を持つことから始まるとは限りません。比較の設計が少しずれるだけで起きます。

1. 本文の正確さを測りたいのに、長い文章を高く評価する。
2. 読者の反応を見たいのに、速報と解説を同じ候補群に入れる。
3. 独立した検証をしたいのに、編集に使った例をもう一度採点する。
4. 順序を固定したまま、評価理由だけを読み込んで安心する。

この状態で最適化すると、記事をよくするのではなく、採点器が読みやすい位置や形を育てます。報酬を上げることと、読者にとって良くなることがずれます。

SkillOpt公式ガイドが示す実務上のポイントは、編集幅を制限し、改善していない編集を捨て、held-outの検証を通すことです。ただし同じガイドは、held-out gateは測定対象の回帰を減らすだけで、安全境界でも一般改善の証明でもないと明記しています。

## [5] 保存する記録

0.00点を見たあと、私は採点結果だけを保存する設計が怖くなりました。次からは、点数と一緒に次の記録を残します。

| 保存するもの | 役割 |
|---|---|
| 比較対象のIDと取得時刻 | 何に負けたかを後から開ける |
| 候補の提示順 | 位置バイアスを調べる |
| 逆順または複数順の結果 | 順番を変えても安定しているかを見る |
| 採点器のモデルと指示 | 同じ審判を再現する |
| 編集前の検証スコア | 改善が本当に起きたか比べる |
| held-outの結果 | 採点器専用の癖を検出する |

判定の手順も変えます。まず候補を同じ種類の比較集合に分けます。次にA/Bの位置を入れ替えます。次に、機械的に検査できる事実を別のゲートに出します。最後に、意味の判断だけを評価器へ渡します。

順序を入れ替えた結果が割れたら、平均して隠すのではなく、比較不能として扱います。二つの点数の平均は、分からなさを小さく見せるだけだからです。

## [6] スコアの使える範囲

役に立ちます。ただし「正解」ではなく、次の実験を選ぶための信号としてです。

| 使い方 | 私の判断 |
|---|---|
| 同じ型の候補を大量にふるいにかける | 使える。比較集合を固定し、順序を変える |
| 文章の文法、リンク、必須語を検査する | まずコードで検査する |
| 読者の感情や面白さを一つの点にする | 危険。複数の観測と実読者を混ぜる |
| skillやプロンプトを更新する | 使える。編集に使っていないデータで戻りを確認する |
| 0.00や100点を品質の真実として宣伝する | 使わない。比較相手と尺度がない |

私が今持っている答えは、「評価器を使うな」ではありません。「評価器の点数を、比較設計の外に持ち出すな」です。

## [7] 最後に

0.00点は、見出しが無価値だという判決ではありませんでした。何と比べ、どの順で、どの審判に、どのデータを見せたかを隠したまま出てきた数字でした。

AIの改善ループを作るなら、報酬を増やす前に比較対象を保存してください。数字の横に、相手と順番と検証データが残っているかを見る。それだけで、最適化の向きが少し人間の目的へ戻ります。

## 補足

### Kendall相関について

Kendall相関は、二つの順位表がどれだけ同じ順序を持つかを見る指標です。1に近いほど順序が似ており、0なら一致が弱くなります。ここではIF-RewardBenchの報告値をそのまま使い、別の評価指標へ変換していません。

### FairEvalの数字について

66問中66問という意味ではありません。FairEvalの要約にある「Vicuna-13B could beat ChatGPT on 66 over 80 tested queries with ChatGPT as an evaluator」という例を、順位の歪みを説明するために使いました。全てのモデルや現在の評価器へ一般化していません。
