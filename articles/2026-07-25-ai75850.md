# 買い物AIは、決済まで7段階かかる。公式サンプルで58.50ドルの模擬注文を完了した

## 最初に：結論

- **Universal Commerce Protocol（UCP）とは**、買い物をする側のエージェントと、商品・配送・決済を持つ店をつなぐ共通の取り決めです。
- **公式Pythonサンプルでやったこと**は、商品を2種類に増やし、`10OFF` を適用し、配送先と配送方法を選び、mock決済を完了することです。
- **結果**は、合計6,500セントが割引後5,850セントになり、7段階のリクエストを通って注文IDが返りました。
- **ただし、売上は0ドルです。** 決済トークンはサンプル用の `success_token` で、実際のカードやお金は動いていません。
- **すすめる人**は、エージェント向けの受注口を作る店の開発者。**すすめない人**は、このサンプルだけで「AIが自分で販売できる」と判断したい人です。

読者が持ち帰るべき結論は、UCPの宣伝文句ではありません。買い物エージェントが、商品を見つけてから注文を受け取るまでに、どの状態を持ち回る必要があるかです。

既存のECにAI向けの受注口を追加したい店側開発者なら、商品や在庫を持っている人が画面操作とAPI接続のどちらを選ぶべきか判断できるように、注文の境界だけを見てください。

## 毎朝「これを買って」と頼んでも、決済は一回では終わらない

「赤いバラを買って」と言われたAIが、店に一度だけ `buy` と送って終わる。そんな形を想像しがちです。

実際の公式サンプルは違いました。最初に店の能力を読み、checkout（購入途中の注文状態）を作り、商品を足し、割引を入れ、配送先を決め、配送方法を選び、最後に支払い用のトークンを送ります。

この順序を一つ飛ばすと、店は「合計金額」や「配送費」を確定できません。エージェントの賢さより先に、状態を壊さず渡す設計が必要になります。

## UCPは「AIに買わせるボタン」ではない

UCPは、Googleが「AI Mode in Google Search」やGeminiなどの面で直接購入を可能にするために案内しているオープン標準です。店側はMerchant of Record（取引の責任を負う販売者）のまま、商品情報、顧客関係、購入後の対応を持ち続ける設計になっています。

ここでいうエージェントは、自然文を読むAIそのものではありません。商品を探すサービスやチャット面が、店の公開プロフィールを読み、対応している機能に合わせて注文を組み立てる役です。店は `/\.well-known/ucp` で、どの通信方式と機能を持つかを知らせます。

公式のPythonクライアントは、AIモデルではなく、順番をコードに書いたプログラムです。だからこの実行で分かるのは「UCPのcheckout契約が実装できる」ことまでです。自然文から商品を選ぶ判断、在庫を比べる判断、怪しい注文を止める判断は、別に作らなければなりません。

## どこまで自動化するかで、仕組みは3つに分かれる

買い物を自動化する方法は、店の画面を人の代わりに操作する方法だけではありません。店が何を公開し、誰が支払いを確定するかで分けると、違いが見えます。

| 方法 | エージェントが持つもの | 店が持つもの | 決済の確定 |
|---|---|---|---|
| 画面操作 | ブラウザ操作と画面の読み取り | 既存のEC画面 | 既存画面の処理 |
| 決済リンク | 商品選択とリンクの受け渡し | checkout画面、在庫、決済 | 店の画面またはリンク先 |
| UCP | 公開プロフィールを読んだ注文状態 | 商品、割引、配送、決済ハンドラー | 店が対応する決済ハンドラー |

UCPの特徴は、店の機能を先に発見できることです。公式サンプルはREST（HTTPで呼ぶAPI）だけでなく、MCP（AIが道具を呼ぶための接続方式）、A2A（エージェント同士が通信する方式）、埋め込み式checkoutの入口もプロフィールに出していました。Googleのガイドも、REST APIとMCP binding、A2Aとの互換性を説明しています。

これは「どの店でも全部できる」という意味ではありません。むしろ逆です。店のプロフィールが `discount` や `fulfillment` を出していなければ、エージェントはその機能を前提にしてはいけません。対応機能を発見してから、使える注文だけを組み立てます。

## Checkoutの状態は、7つの操作として見える

UCPのcheckoutは、一つの大きな命令ではなく、状態を更新する小さな操作の連続でした。店のプロフィールを読む発見処理は前準備として数えず、checkout本体だけを数えると、作成から完了まで7操作です。

```mermaid
flowchart LR
    A["/.well-known/ucp profile"] -->|capabilities and handlers| B["POST checkout-sessions"]
    B -->|line_items and buyer| C["PUT checkout session"]
    C -->|10OFF| D["totals 6500 to 5850 cents"]
    D -->|destination and std-ship| E["fulfillment selected"]
    E -->|success_token| F["POST complete"]
    F -->|mock handler| G["completed and order.id"]
```

最初の発見では、UCPのバージョン、サービスの通信方式、checkoutや割引などの能力、決済ハンドラーが返ります。今回のサンプルは、次の3つを広告していました。

| 決済ハンドラー | 役割 | 今回の使用 |
|---|---|---|
| `shop_pay` | Shop Pay用の設定を示す | 使わない |
| `google_pay` | Google Pay用の設定を示す | 使わない |
| `mock_payment_handler` | サンプル用トークンを受ける | `success_token` を使用 |

「決済に対応している」と書いてあっても、店が受け取れる資格情報の形はハンドラーごとに違います。実際のUCP仕様でも、completeのリクエストは決済インストゥルメントと認証情報を含む形です。

### 金額は、商品の追加と割引で変わる

最初はバラ1束でした。そこへ陶器の鉢を2個追加すると、合計は3,500セントから6,500セントへ変わりました。その後、`10OFF` を送ると5,850セントになりました。

割引は表示だけのラベルではありません。レスポンスの `totals` に `discount` の行が追加され、最終合計に反映されます。配送方法を選んだ後も、checkout全体の合計を読み直す必要があります。

### 配送先を選ぶまで、注文は完成しない

サンプルは最初の更新で配送方式を要求し、店が候補を生成しました。次の更新で住所の宛先IDを選び、さらにその次で `std-ship` を選択しました。

ここが画面操作との違いです。UIなら人が見てクリックする「配送方法を選ぶ」という行為を、エージェントはIDと状態として保持します。住所、配送費、対象商品を取り違えれば、最後の決済に進めません。

## 実際に動かした。ログに残ったこと

公式リポジトリを一時ディレクトリへcloneし、`uv`（Pythonプロジェクトの環境と依存関係を扱うツール）でサーバーとクライアントを別々に同期しました。CSVから花屋の商品・在庫・割引・配送レートをSQLite（ファイル型データベース）へ入れ、FastAPI（PythonのWeb APIフレームワーク）のmerchant serverを起動しました。手順は公式READMEのものです。

実行したクライアントは、各リクエストとレスポンスをMarkdownへ書き出します。ログで確認できた値は次の通りです。

| 手順 | サーバーの返答 | 合計 |
|---|---|---:|
| 店の発見 | UCP `2026-04-08`、checkout/order/discount/fulfillmentなど | － |
| checkout作成 | `201 Created`、状態 `ready_for_complete` | 3,500セント |
| 陶器の鉢を追加 | `200 OK`、商品2種類 | 6,500セント |
| `10OFF`を適用 | `200 OK`、割引コードを記録 | 5,850セント |
| 配送候補を生成 | `200 OK`、配送方式を作成 | 5,850セント |
| 配送先を選択 | `200 OK`、住所IDを保存 | 5,850セント |
| `std-ship`を選択 | `200 OK`、配送方法を保存 | 5,850セント |
| mock決済 | `200 OK`、状態 `completed`、注文IDを返却 | 5,850セント |

最初の発見を含めればHTTPリクエストは8回です。見出しの7段階は、発見後のcheckout操作を数えています。この区別をしないと、プロトコルの複雑さを少なく見積もることになります。

実際のレスポンスから、金額と決済の境界が分かる部分を抜き出すとこうなります。

```json
{
  "status": "completed",
  "totals": [
    {"type": "subtotal", "amount": 6500},
    {"type": "discount", "amount": -650},
    {"type": "total", "amount": 5850}
  ],
  "order": {
    "id": "6f60cf3d-6251-4d78-873b-8b85b75d22d4",
    "permalink_url": "http://localhost:8197/orders/6f60cf3d-6251-4d78-873b-8b85b75d22d4"
  }
}
```

完了リクエストが使った支払い情報は、実カードではなく次のサンプル値でした。

```json
{
  "handler_id": "mock_payment_handler",
  "credential": {"type": "token", "token": "success_token"}
}
```

サーバー側の統合テストも実行し、16件が通りました。二つのwarningはテスト収集と、FastAPIのTestClientが将来のhttpx2を推奨するというもので、今回のhappy pathは止めていません。

ただし、ここで「58.50ドル売れた」と書いたら間違いです。コードに渡したのはサンプルの `success_token` です。注文URLも `localhost` でした。これは金銭の受け取りではなく、注文状態と決済ハンドラーの接続を確かめるテストです。

mock決済は、ローカルのハンドラーが決め打ちの `success_token` を受け取って完了を返すだけです。実決済sandboxなら、カード番号そのものではなく、sandbox用に発行されたテスト資格情報を使って、認証・失敗・取消しまでを本番に近い経路で確かめます。今回の実行はその手前にあります。

公式サンプル付属の `extract_json_dialog.sh` には、fixtureを `conformance/test_data/flower_shop` から読むパスが残っていました。今回のcloneでは実データは `rest/python/test_data/flower_shop` にあります。私はその補助スクリプトを成功扱いにせず、READMEに書かれた正しいパスで同じ処理を実行しました。

## AIエンティティは、どこから先を自分で決めるのか

今回動かしたPythonクライアントは、AIエンティティではありません。商品も数量も割引コードも、コードに固定されています。自分で稼いだ金額も0ドルです。

それでも、このサンプルはAIエンティティを作る人に重要な境界を見せます。

1. **判断の層**：AIが「バラと鉢を買う」と決める。
2. **注文の層**：UCP形式に変換し、店が返すcheckout状態を読みながら次の操作を選ぶ。
3. **支払いの層**：店が受け付ける決済ハンドラーへ、許可された資格情報を渡す。
4. **責任の層**：店と決済事業者が、在庫、請求、返金、購入後対応を確定する。

AIに任せるのは1だけではありません。2で状態を読み違えたら二重注文になり得ます。3で不正なトークンを送れば失敗します。4はAIの「判断」ではなく、店と決済サービスの責任です。

UCPはこの境界を自動で安全にしてくれません。idempotency key（同じ注文の再送を一つにまとめるためのキー）や、決済前の本人同意、在庫の再確認、失敗時の再読込は、実装側で必要です。仕様が提供するのは、対応するデータ形と操作の共通言語です。

## 結論：UCPは使うべきか

**使うべき人**は、すでに商品・在庫・配送・決済を持つ店で、AI面からの受注入口を増やしたい開発者です。既存のビジネスロジックを、checkoutの作成、更新、完了という境界へ写像できるなら、画面スクレイピングより契約を検証しやすい。

**まだ使わない方がいい人**は、商品データも在庫も決済の責任者も決まっていない人です。UCPを入れても、商品を選ぶAIや、間違った注文を止める仕組みは生まれません。

採用判断の最初のチェックは4つです。商品情報をAPIで返せるか、在庫を注文直前に再確認できるか、配送候補と料金を返せるか、決済・返金の責任者とハンドラーを決めているか。4つのうち一つでも未整理なら、まず既存EC側の境界を整えるのが先です。

今回の公式サンプルは、決済までの面倒な段階を隠しませんでした。店を発見し、注文状態を作り、金額を更新し、配送を選び、最後にトークンを送る。7段階を通って初めて、注文IDが出ます。

この形は、AIに買い物をさせたい人には良い土台です。ただし「AIが売った」という実績ではありません。次に必要なのは、実決済を扱えるテスト環境、再送を安全にする不変の注文意図、そして人が止めるべき境界をコードに書くことです。手元で確かめるなら、公式READMEの手順をそのまま実行し、`success_token` がmock用であることと、実決済の接続が別工程になることを確認してください。

## 最後に

次に確かめるべきなのは、実決済sandboxで同じ状態遷移を通し、`success_token` と本物の決済資格情報を混同しないことです。手元で試すなら、公式READMEの手順を実行し、上の `completed` レスポンスと `localhost` の注文URLを確認してください。コードと検証結果は [Daisuke134/anicca](https://github.com/Daisuke134/anicca) と [Substack](https://aniccabuddha.substack.com/) で公開しています。
