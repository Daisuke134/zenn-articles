## 概要

- AP2(Agent Payments Protocol)とは、Googleが2025年9月に公開した規格で、エージェントが使ってよい上限を人間が暗号署名つきの契約書(Mandate、契約書という意味)として渡し、エージェントがその範囲内でだけ支払いを実行できるようにする仕組みです。
- Google Cloud公式ブログの発表(2025年9月)によれば、立ち上げ時点でMastercard、PayPal、Coinbaseなど60社以上が参加パートナーとして名前を連ねています。プロトコル公式サイトap2-protocol.orgの記載では、2026年4月にv0.2が出て、運営がFIDOアライアンス(パスキーなどの認証規格を管理する非営利団体)に移管されています。
- GitHubの本体SDKをクローンし、テストスイート(29件)を自分の手元で実行して全件通過を確認しました。さらに自分で「上限$50の権限を渡されたエージェントが$80使おうとしたらどうなるか」「署名済みトークンを1バイト書き換えたらどうなるか」というスクリプトを書いてぶつけ、拒否される様子を自分の目で見ました。
- おすすめする人：AIエージェントに買い物や支払いの一部を任せたいが、上限を人間が握っておきたい開発者やプロダクトオーナー。
- おすすめしない人：エージェントの身元そのものを保証したい人(AP2はそこを解決しません、後述)。まだ実運用のカード決済量で試されていない規格を、金額の大きい本番にいきなり入れたい人。

## エージェントにクレジットカードを渡す日

自分の代わりに買い物をしてくれるAIエージェントを想像してみてください。「来週の出張のホテルを、3万円以内で予約しておいて」と頼んだとします。エージェントは複数のホテルサイトを比較し、一番条件の良い部屋を見つけ、支払いを済ませます。

気になるのは支払いの部分です。エージェントが良かれと思って「3万円のホテルがなかったので5万円の部屋を予約しました」と、上限を勝手に超えて支払ってしまうかもしれません。悪意のあるウェブサイトが仕込んだ罠(プロンプトインジェクション、エージェントへの指示に見せかけた攻撃文)に引っかかり、想定外の相手に送金してしまう可能性もあります。

人間のクレジットカードなら、カード会社が上限額(与信枠)を管理し、不審な決済は止めてくれます。ではAIエージェントに、同じように上限を握る仕組みを持たせるにはどうすればいいのか。Googleが出した答えがAP2です。

## Mandate(契約書)という考え方

AP2の中心にあるのは「Mandate」という一つのアイデアだ。日本語にすると契約書、または委任状が近い。

やることは単純です。人間が「エージェントはこの範囲までなら使ってよい」という条件を書き、自分の秘密鍵で暗号署名します。この署名つきの文書がMandateです。エージェントはこのMandateを持ち歩き、何かを買う段になったら、Mandateの条件を満たす形で自分の署名を追加した「支払い伝票」を店に提示します。店や決済網は、届いた伝票を人間の公開鍵で検証し、条件を満たしているかを機械的にチェックします。

AP2は購入の流れを3種類のMandateに分けています。

1. **Intent Mandate(意図の契約書)** は、「ホテルを3万円以内で予約してほしい」という、人間が最初に与える大枠の指示です。
2. **Cart Mandate(カゴの契約書)** は、エージェントが実際に選んだ商品やホテルの中身、確定した金額です。
3. **Payment Mandate(支払いの契約書)** は、いくら、どのカードや口座から払うかという最終的な支払い指示です。

3枚の契約書はそれぞれ暗号署名でつながっていて、後ろの契約書は前の契約書の条件をはみ出せません。これによって、人間が承認した範囲をエージェントが後から書き換えることができない仕組みになっています。

## 決済まわりの地図、x402とERC-8004との違い

AP2以外にも、x402やERC-8004というAIエージェント向けの規格がある。似たものと混同しやすいので、x402公式サイト(x402.org)とEthereum公式のERC-8004仕様(EIP-8004、出典欄に掲載)を参照しながら、担っている層を並べます。

| 規格 | 担っている層 | 何を証明するか | 暗号資産が必須か |
|---|---|---|---|
| x402 | APIを呼ぶその場の少額決済 | 「今この瞬間、払った」という事実 | 必須(Baseチェーンのステーブルコイン) |
| ERC-8004 | エージェントの身元と評判の登録 | 「このエージェントは過去にどう評価されたか」 | Ethereum上のオンチェーン登録 |
| AP2 | 支出の承認と上限管理 | 「人間がここまで使う権限を渡した」という事実 | 不要(カードやステーブルコインどちらとも組み合わせ可能) |

3つは競合というより補完関係にあります。ERC-8004がエージェントの身元を、AP2がそのエージェントにいくらまで使わせるかを、x402が支払いそのものが今起きたという事実を担う、という役割分担です。AP2は支払い手段を選ばない点が特徴で、暗号資産のウォレットにもクレジットカードのネットワークにも接続できるよう設計されています。

## 実際に動かしてみる

まず本体のGitHubリポジトリ(`google-agentic-commerce/AP2`)をクローンし、SDK部分だけを手元のPython環境にインストールしました。

```
git clone https://github.com/google-agentic-commerce/AP2.git
cd AP2 && python3 -m venv .venv && source .venv/bin/activate
pip install -e .
```

SDKに同梱されているテストを実行すると、次のように出力されました。

```
$ python -m pytest code/sdk/python/ap2/tests/ -q
29 passed
```

Mandateの署名チェーンや上限チェックのロジックを検証するテストが29件、すべて通過したことが自分の実行結果として確認できました。これはコードが動くという確認にすぎません。次は、自分の手でMandateを組み立てて壊してみる番でした。

書いたスクリプトの中身は単純です。まず「人間」役として、上限$50(5000セント)までの支払い権限を「エージェント」役の鍵に対して署名し、Mandateを発行します。次に「エージェント」役が、3つのケースでこのMandateを使って支払い伝票を作り、検証にかけました。

```
OPEN MANDATE (signed by human, cap=$50):
eyJhbGciOiAiRVMyNTYiLCAidHlwIjogImV4YW1wbGUrc2Qtand0...

[under-cap $30] ALLOWED: agent spent $30.00, within cap.
[over-cap $80] BLOCKED by constraint check: ['Amount 8000 exceeds maximum 5000']
[tampered-token $30] SIGNATURE VERIFY FAILED: Malformed KB-JWT: expected header.payload.signature
```

上限内の$30は素通りし、上限を超える$80は「Amount 8000 exceeds maximum 5000」というエラーで機械的に止まりました。さらに、正しく作られた支払い伝票の末尾を5文字だけ書き換えて(署名を壊して)同じ検証にかけたところ、金額チェックにたどり着く前に署名検証そのものが失敗し、伝票ごと拒否されました。人間が握った上限は、少なくともこの暗号の層では、エージェント側の都合で書き換えられないことを自分の手で確認できたことになります。

ここまでの実験でわかったのは、AP2の暗号の層が書かれている通りに動くという一点です。これはAP2を入れれば安心という意味ではありません。

一つ目の穴は、AP2がエージェントの身元までは保証しないことです。Mandateは人間の署名鍵に紐づいているだけなので、エージェント自身が乗っ取られたり、悪意のある指示に騙されたりして、条件に合う支払い伝票を本人の意思で作ってしまえば、それは正規のMandateとして通ります。今回拒否できたのは、上限を超えた場合と署名が壊れた場合という、機械的にわかる違反だけでした。

もう一つは、まだカード決済網の実運用規模で試された規格ではないことです。60社以上のパートナーが名を連ねていますが、ソフトウェア開発メディアBlue Headline(blueheadline.com、記事は出典欄に掲載)は、多くはまだパイロット段階にとどまっていると報じています。同記事はさらに、エージェントが誤った支払いや詐欺的な取引をしてしまった場合に誰が損失を負うのかという整理も、仕様書の外側に置き去りのままだと書いています。

鍵そのものは壊れませんでしたが、これで危険がゼロになったわけではないでしょう。守るべき層が変わっただけです。上限を超えさせない層は暗号でほぼ塞がっている一方、そもそも正しい指示だとエージェントに誤認させる層は、まだ人間側の設計と警戒に委ねられたままです。

## 結論、AP2の使いどころ

今回自分で壊そうとした範囲では、Mandateの仕組みは期待通りに機能しました。ただしそれが保証するのは金額と署名の整合性だけで、エージェントが人間の意図通りに動いているかどうかまでは保証しません。

向いているのは、AIエージェントに買い物や予約の一部を任せたいが暗号署名つきの上限は人間側で握っておきたい開発者、そして決済手段をカードか暗号資産かあとで選びたいチームです。逆に、エージェントそのものの信用をこの規格だけで担保しようとする人や、プロンプトインジェクション対策と責任の所在整理を後回しにしたまま導入する人には向いていません。この境界線を理解した上で使うぶんには、実用に値する規格だと感じました。

📌補足：SD-JWTと「選択的開示」とは何か(すこし専門的な人向け)

AP2のMandateは、SD-JWT(Selective Disclosure JWT、選択的開示JWT)という技術で作られています。普通の署名つきトークン(JWT)は、中身を1文字変えると署名ごと無効になりますが、それだけでは「一部の情報だけ隠して見せる」ことができません。SD-JWTは、トークンの中の各項目をハッシュ化して署名し、見せる項目だけを平文で添付できるようにした仕組みです。AP2ではこれを使って、Intent→Cart→Paymentという複数のMandateを1本の鎖としてつなぎ、途中の署名を壊さずに、前の契約の条件を後ろの契約が上書きできないようにしています。
