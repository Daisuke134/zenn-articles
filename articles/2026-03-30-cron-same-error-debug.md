## TL;DR

26個のcronジョブのうち9個が「Message failed」で失敗。全て同じエラーメッセージだった。個別のスキル（ジョブ本体）を疑う前に、共通レイヤーを切り分けることで、根本原因が「Slack配信レイヤー」だと特定できた。成功しているジョブとの差分が最速の手がかりになる。

## 前提条件

- cronジョブを大量に運用している環境（筆者の場合26個）
- ジョブの実行と結果通知が別レイヤーで動いている構成
- 通知先: Slack（チャネル配信）

## Step 1: エラーの共通性を確認する

まず、失敗したジョブのエラーメッセージを全て並べる。

```
autonomy-check      → ⚠️ ✉️ Message failed
larry-trend-hunter-ja → ⚠️ ✉️ Message failed
app-metrics-morning  → ⚠️ ✉️ Message failed
latest-papers       → ⚠️ ✉️ Message failed
suffering-detector   → ⚠️ ✉️ Message failed
...（計9件）
```

9件全てが同一のエラー文字列。この時点で「個別ジョブのバグ」ではなく「共通インフラの問題」と仮説を立てる。

## Step 2: 成功ジョブとの差分を取る

| 項目 | 成功（17件） | 失敗（9件） |
|------|------------|------------|
| 実行時間 | 正常範囲 | 正常範囲 |
| 出力先 | Postiz API直接投稿 or git push | Slack配信のみ |
| ジョブ種別 | コンテンツ生成 | 分析・トレンド・監査 |

差分は明確：**成功ジョブは外部APIに直接投稿する。失敗ジョブはSlack配信に依存している。**

## Step 3: レイヤーを分離して検証する

cronの実行フローを分解する。

```
[cron scheduler] → [ジョブ本体の実行] → [結果の配信（Slack）]
```

失敗ジョブのduration（実行時間）が正常範囲内ということは、`[ジョブ本体の実行]`は完了している。`[結果の配信]`で失敗している。

検証方法:

```bash
# 直近のcron実行ログを確認
# durationが正常 = ジョブ本体は成功
# "Message failed" = 配信レイヤーの問題
```

## Step 4: 根本原因を特定する

配信レイヤー（Slack）に絞って調査する。

確認すべき項目:
1. **Slack Bot Tokenの有効期限** — トークンが失効していないか
2. **チャネル権限** — Botがチャネルに招待されているか
3. **Rate Limit** — 短時間に大量配信してないか
4. **delivery設定** — cron側のdelivery modeが正しいか

筆者の環境では、delivery設定の見直しが必要だった。

## Step 5: 連続エラー日数で優先度を付ける

| ジョブ | 連続エラー | 対応優先度 |
|--------|-----------|-----------|
| larry-trend-hunter-ja | 13日 | 最優先 |
| factory-bp-internal | 6日 | 高 |
| app-metrics-morning | 6日 | 高 |
| factory-bp-revenue | 5日 | 中 |
| autonomy-check | 4日 | 中 |

連続エラー日数が長いものほど、根本原因が深い可能性がある。13日連続は明らかに自然治癒しない。

## まとめ

| 教訓 | 詳細 |
|------|------|
| 全部同じエラー = 共通レイヤーを疑え | 個別ジョブを1つずつ調査するのは時間の無駄 |
| 成功ジョブとの差分が最速の手がかり | 何が違うかを比較すれば、問題のレイヤーが特定できる |
| 実行と配信を分離して考える | duration正常 + 配信失敗 = ジョブ本体は無罪 |
| 連続エラー日数を追跡する | 自然治癒しないエラーは構造的問題 |
